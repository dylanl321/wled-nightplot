# Push motion maps with Looks, hang-to-effects slice 2 (v2)

Fix commit 696ed2a closes the two blocking v1 findings. A push that needs no map now overwrites an older base `ledmap.json` with a straight one (rereading it) before any preset naming map 0 is sent. A multi-file write that fails partway names the files already left on the controller and records them in `lastLedmap`. Re-push tests were added for both paths and for fewer maps on a second push. What remains is small: the reset rewrites the identity map on every later no-map push, and the file that fails its own reread is not recorded.
Watch for: the stale-base reset rewrites `ledmap.json` on every no-map push once the record has a slot 0 row (confirmed); a map file that was written but failed its reread is absent from the record, so the record can hold an older digest than the board (likely); the stale-map probe swallows read errors and sends presets anyway (confirmed, narrow).

**Verdict**: APPROVED

## High-level view

The stale-base-map problem is handled in the push route. When the plan has no writes, `staleBaseMapReset` decides whether an old base map may exist (the record has slot 0, or the controller returns a non-identity map) and, if so, the identity map goes through the same write-and-reread path as any other map. Presets are still sent only after that verifies.

Partial-write failures now return the written file names in the message and persist them via `mergeLastLedmap`, so the app's record follows the board for files that verified. Unused slots from earlier pushes are left alone and keep their record rows.

Preview still sends no `ledmap` and End Preview cannot restore a map number. That is a documented gap in the changelog and `docs/hang-to-effects.md`, tied to the slice 0 bench, and is accepted here. Yard check still covers slot 0 only; all-digest comparison is slice 6.

## Reset on every no-map push

```
record has slot 0 row  -> reset (always)
record empty           -> read board; identity -> nothing, else reset
```

The record branch never compares digests. After a first reset the record holds slot 0 with the identity digest, so each later push of a no-map Light writes and rereads `ledmap.json` again. Harmless to correctness but it is an extra flash write per push per Light, and a failure of that write blocks a push that would otherwise need nothing. The test "a later push that needs no map" confirms the first reset but does not cover a third push.

## Record versus board on a failed file

`writeAndVerifyLedmap` pushes to `written` only after the reread matches. On a mismatch or a reread failure, the failing slot is not in `written`, and the route's failure path merges only `written`. The test for mismatch asserts the record shows slot 0 only, which pins this behaviour. If slot 1 previously held a different map, the record claims the old digest while the board may hold the new one. Presets are not sent, so Looks still name their old maps, but they now point at a changed file until the next successful push.

## Probe errors

`staleBaseMapReset` catches read failures and returns no writes. Combined with presets naming map 0, this means an unrecorded stale base map can survive silently. A note in the result would make that visible.
