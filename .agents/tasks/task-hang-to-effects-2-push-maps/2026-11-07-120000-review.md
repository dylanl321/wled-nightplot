# Push motion maps with Looks, hang-to-effects slice 2 (v1)

A Look push now plans every light map the Light needs (`planLightMaps`), writes each distinct `ledmapN.json`, rereads and compares each, and only then uploads presets. Every Look preset names its map with `"ledmap"`, and Off and playlist presets name map 0. Segment ranges in a mapped Look are map positions, with `rev` taken from the map. Drawn-vs-attached count mismatches and more than nine extra maps are refused before any write. `lastLedmap` becomes a per-slot list with legacy migration. Lint, typecheck and all tests pass; the fixture box is not WLED, so nothing here is verified on a board.
Watch for: a push that needs no map writes nothing, yet its presets say `ledmap 0`, so a `ledmap.json` or `ledmapN.json` left by an earlier push stays on the board and can still apply (likely); Preview sends no `ledmap`, so it runs against whichever map the last recalled preset loaded (likely); a multi-map write that fails partway reports "Nothing else was sent" although earlier map files are already on the controller (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The design splits cleanly into a pure planner and a server writer. `planLightMaps` places each prop (attachment, "after" chains, output offset, legacy segments), refuses on count disagreement, then hands Look motions to the slice 1 builder. The server writes all maps and verifies them before touching presets, which keeps the "unverified write is not success" rule intact for every file.

Presets are re-ranged into map positions per Look. A prop whose block is unchanged in the Look's map keeps physical targets; others get one target per section plus rest ranges. Every preset now carries an explicit `ledmap`, which is the right call for never inheriting the last map, but it makes the state of the files on the board part of the contract.

The weak spot is that state. Nothing removes or overwrites map files a previous push left behind, and Preview and the Yard check don't know about maps beyond the base. The docs correctly mark these defaults as pending the slice 0 bench.

## Stale map files after a push that needs none

`planLightMaps` returns `writes: []` when there is one map and it is the identity. `pushLooksToLight` then skips the write, but `buildLookPreset` still emits `"ledmap": 0`. Map 0 means `ledmap.json`, so if an earlier push (for example a Look with Downward motion, later changed to Wire) left a non-identity `ledmap.json`, the presets now silently run on it while their segment ranges are physical. The same applies to a slot 1 to 9 file no preset names any more, which is harmless, but base-map staleness is not. Bench row 3 tests only "no file", not "old file". The test "writes no map file and sets ledmap 0" runs on a fresh box and so cannot see this. The fix is cheap: when `lastLedmap` has a slot 0 row (or the reread finds a file) and the new base is identity, write the identity map and verify it.

## Preview and maps

`look-live-routes` is untouched and sends no `ledmap`. A Light that last recalled a mapped preset keeps that map loaded, so Preview's physical ranges land on the sorted order. The docs list this in bench row 11 as something to observe, but it is a regression in what Preview shows relative to the pushed Look, not only a hardware question.

## Partial writes across maps

Maps are written in order and the loop stops at the first failure. The messages keep the old single-file wording "Nothing else was sent". With nine maps, a failure at slot 4 leaves slots 0 to 3 changed on the board while `lastLedmap` is not updated, so the app's record and the board disagree until the next successful push. Presets are not uploaded, so Looks still point at the old maps, which is safe, but only if the old base map was not overwritten with a different order. The slot 0 file is written first, so a later failure can leave preset ranges and the base map out of step.

## Yard check and recorded digests

Expected presets now include `ledmap` and map-position ranges, so older pushes show as different until re-pushed. `compareLedmap` and the season `ledmapJson` still look at slot 0 only (slice 6).
